## 1. 目标与交付物

**目标**：服务器只有 3 M 带宽、无 CDN → **不重复下载**、**不白下大资源**、**手机端不卡**，
并且修掉 2026-10-12 真机暴露的两处"看护自身造成的卡顿/误报"。

| 交付物 | 实现 |
|---|---|
| 首屏看护去误报（本块重点） | `shell/feel/RenderWatchPolicy.kt`（纯逻辑）+ `FeelHost` 接线：复核对 5/12/25/45 s **多次重试**，只有**连续两次**空 DOM 且到点才列诊断；诊断浮层出现后按 2/4/8/15/30 s **轮询撤销**，内容一出现立刻撤掉 |
| 状态探测降频/按需 | `shell/feel/ProbeCadence.kt`（纯逻辑）：稳定逐档退避 `2 s → 4 s → 8 s → 15 s`（低内存档上限 30 s），**有变化立刻回 2 s**；`PageStateProbe` 间隔改为动态（硬下限 1500 ms） |
| 大资源兜底拦截（Live2D） | `shell/perf/HeavyAssetPolicy.kt` + `PerfHost.interceptHeavyAsset` + `WebShellClient.shouldInterceptRequest`：命中 `AppConfig.BLOCKED_ASSET_PREFIXES`（`/static/live2d/`）返回**空体 200**；主文档永不拦；清单开关 `blockLive2dAssets`（默认开）可远程关 |
| 设备分级与低内存降级 | `shell/perf/DeviceClass.kt`（纯逻辑）：`isLowRamDevice` / `memoryClass` / 可用存储 → 两档；低内存档探测更慢、内存缓存更愿意清、存储阈值更保守 |
| 缓存清理时机（不重复下载） | `shell/perf/CacheTrimPolicy.kt`（纯逻辑）+ `PerfHost`：**默认什么都不做**，只在"空间告急 / 低于档位阈值 / 超过 30 天"时清磁盘缓存；内存缓存只在系统报告内存压力时清（`clearCache(false)`，不动 Cookie） |
| 轨迹落盘复用 | `shell/DiagLog.kt`（从 FeelHost 抽出的公共件，PerfHost 共用） |
| 静态预检 | `scripts/preflight-perf.sh`（**10 组规则**，含"跨包引用必须显式 import"与"属性初始化不得自引用"，由 `preflight-feel.sh` 连带执行 → **CI 工作流无需改**） |
| 单测 | 5 个测试文件、**47 个新用例**（合计 236 个用例全绿） |

**新增依赖：0**；**新增权限：0**（`ACCESS_NETWORK_STATE` 区块 1 起就在）。

## 2. 关键设计与取舍

### 2.1 ADR-A13：看护只能"多试几次"，不能"一次定生死"

原实现：`onPageFinished` 后 **5 秒复核一次**，空 DOM 就弹诊断浮层，而**撤销点只有
`onPageFinished` 一处**（已经过去了）→ 慢速首屏（3 M 带宽 + 大图首页）必现"诊断浮层一直挂着"。
新实现把"结论"与"撤销"分开：结论要**多次复核 + 连续两次空白**，撤销由**独立轮询**负责。
硬看门狗（12 s，纯计时）也从"无条件举诊断"改成**先探测再下结论**。

### 2.2 ADR-A14：探测按需退避（并且退避是安全的）

探测的两个用处是"网页主题色 → 状态栏配色"和"滚动位置**兜底补正**"。
滚动与手势的**主**信息源是 `ScrollAwareWebView.onScrollChanged`（同步、零开销、不依赖 JS），
所以把轮询从固定 2 s 退避到 15 s/30 s **不会**让"返回顶部"或下拉刷新变迟钝；
系统深浅色变化会重建 Activity（`onResume` 也会立刻探测），最多晚一个退避周期。

### 2.3 ADR-A15：大资源只在**壳侧**兜底，正解仍在网站侧

用户明确要求"App 上不展示 live2d"。实测（2026-10-13 生产 `access.log` 按 UA 过滤）：
网站**已经**按"窗口宽度 ≤ 1024 px 不挂载看板娘"挡住，App UA **零 `/static/live2d/` 请求**。
因此本块做的是**兜底**（网站改规则 / 个别 ROM 视口偏大时也不会白下 60 MB），
不重复实现网站侧逻辑；网站侧的 UA 判断仍按 ROADMAP 归区块 8。

### 2.4 明确**不做**的三件事（2026-10-13 与管理员确认）

| 事项 | 决定 | 理由 |
|---|---|---|
| "首屏关键资源预取" | **不做** | 实测瓶颈是图片（3.4 MB）而不是 JS（74 KB），预取会抢 3 M 带宽，还与 L0 热更新（秒级生效）冲突；改为"不重复下载"（收敛 clearCache 时机） |
| "仅 WiFi 下载大资源" | **不做** | 蜂窝下拦 `/media/panorama/` 会让全景页显示破图/空白，而页面本身没有"需 WiFi"提示；体验代价大于收益 |
| 远程开关快照（供 PushHost 读 flags） | **不做** | 区块 5 报告里留的待办，本块不扩大范围 |

### 2.5 实测数据（本块决策的依据）

生产 `access.log`（App UA 会话，约 1 小时）：

| 项目 | 实测 |
|---|---|
| 会话总流量 | **4.75 MB**（172 请求） |
| 最大单项 | 新闻封面**原图 1.41 MB** + 正文配图 1.07 MB / 245 KB |
| JS/CSS | 仅 **74 KB**（nginx gzip 生效） |
| `/static/live2d/` | **0 次** |
| `/media/panorama/` | **0 次** |

结论：**图片是唯一的大头**，而它属于网站侧（缩略图/懒加载，区块 8）；
壳侧能做且值得做的只有"别白下大资源 + 别重复下载 + 别自己耗电"。

### 4.3 CI 首次跑红：一处只有真编译器能发现的错误（已修，并固化成规则）

第一次推完 CI 就在 `:app:compileDebugKotlin` 报：

```text
FeelHost.kt:285:61 Type checking has run into a recursive problem.
```

原因：`clearPoll` 这个属性是 `object : Runnable`，而它自己的初始化块里
（进到内层 `probeContent { }` lambda 之后）又引用了 `clearPoll` —— Kotlin 无法据此推断属性类型。
修法：进 lambda 前先取一个**带显式类型**的局部引用，再用它：

```kotlin
val self: Runnable = this
revealHandler.postDelayed(self, next)
```

两点教训已固化：

1. 新增预检第 **10** 组规则「属性初始化块里不得引用属性自身」（反向注入验证能拦住）；
2. 这类错误**本地编译不出来**（`FeelHost.kt` 依赖 androidx/R 类，本地无 Android SDK），
   本块的做法是先用 kotlinc 写一个最小 stub **复现同一个报错**、确认修法能编译，再走通道推上去 ——
   stub 复现 + 修复后编译通过，与 CI 结果（`Debug APK` success）一致。
